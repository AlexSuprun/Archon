# 5.2 Skills, MCP, hooks, sub-agents

What this answers: per-node Claude-only capabilities — what each YAML field does, when to reach for it, and gotchas.

## Capability matrix

| Field | Claude | Codex | Pi | Translates to |
|-------|--------|-------|----|---------------|
| `skills` | Yes | No | Limited (Pi-native skills, no AgentDefinition) | Internal `dag-node-skills` AgentDefinition |
| `mcp` | Yes | No | No | `mcpServers` + wildcard `mcp__<name>__*` in `allowedTools` |
| `hooks` | Yes | No | No | SDK `hooks` map (event → matchers) |
| `agents` | Yes | No | No | SDK `agents` map, callable via Task tool |

All four are silently ignored by Codex. For Pi, skills are passed through to the Pi harness only; everything else is ignored. If you need cross-provider behavior, put the logic in the prompt or a `script:` node.

## skills

What it is: a list of skill names preloaded for the node's agent.

```yaml
nodes:
  - id: review
    prompt: Review the diff using the security skill.
    skills: [security-audit, lint-fixes]
```

Translation (Claude only): Archon synthesizes an internal `AgentDefinition` with id `dag-node-skills`, sets it as the primary `agent`, copies `tools` over, and adds the `Skill` tool to `allowedTools`. The agent prompt tells the model: "You have preloaded skills: …".

When to use: you want a node biased toward specific skills without rewriting the prompt.

Gotchas:
- If you also set `agents:` with the key `dag-node-skills`, your definition overrides the wrapper (logged as `claude.inline_agents_override_skills_wrapper`). User wins by design.
- The skills list reaches the SDK as part of an `AgentDefinition`. If you need finer control (different tools, different model per skill bundle), write your own entry in `agents:` instead.

## mcp

What it is: a path to an MCP server config file (JSON). Loaded and forwarded to the Claude SDK.

```yaml
nodes:
  - id: query
    prompt: Look up the issue in linear.
    mcp: .archon/mcp/linear.json
```

Translation: Archon reads the file relative to `cwd`, expands `$VAR_NAME` references in `env` and `headers` blocks against `process.env` at execution time, sets `mcpServers`, and adds wildcards `mcp__<server>__*` to `allowedTools` so the model can call those tools without per-tool whitelisting.

When to use: external integrations (issue trackers, search, vector stores) the model should call directly.

Gotchas:
- Env expansion is at execution time, not at YAML parse time. Missing vars become empty strings — the MCP server may fail auth. Archon emits a `mcp_env_vars_missing` warning listing the missing names.
- Haiku models do not support tool search (lazy loading for many tools). With many MCP tools loaded, switch to Sonnet or Opus. Archon emits `mcp_haiku_tool_search` warning.
- Use `env:` in `.archon/config.yaml` (per-codebase env vars) to feed the expansion when the value is project-scoped.
- The path is a single string, not an array. Compose multiple servers in one config file.

## hooks

What it is: per-node SDK hook callbacks with static JSON responses. Lets you intercept tool calls and lifecycle events.

```yaml
nodes:
  - id: build
    prompt: Run the build.
    hooks:
      PreToolUse:
        - matcher: "Bash"
          response: { decision: "allow" }
          timeout: 30
```

Supported events: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `UserPromptSubmit`, `SessionStart`, `SessionEnd`, `Stop`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PermissionRequest`, `Setup`, `TeammateIdle`, `TaskCompleted`, `Elicitation`, `ElicitationResult`, `ConfigChange`, `WorktreeCreate`, `WorktreeRemove`, `InstructionsLoaded`.

When to use: gate tool calls, inject decisions, redact data before/after tool use.

Gotchas:
- `response` is a static `SyncHookJSONOutput` — Archon does not support dynamic hook callbacks defined inline in YAML.
- Per-node hooks merge with Archon's internal `PostToolUse` capture hook (used for tool-result tracking). Your matchers prepend; the internal one stays.
- Hook event names are case-sensitive. The schema is `.strict()` — a typo like `preToolUse` rejects the YAML at load time.
- `matcher` is a regex against tool names (for `PreToolUse`/`PostToolUse`) or event subtypes.

## agents (sub-agents)

What it is: inline `AgentDefinition` map. Sub-agents are not the primary agent — they're invokable by the main agent through the Task tool.

```yaml
nodes:
  - id: plan
    prompt: Plan the change. Delegate research to the researcher sub-agent.
    agents:
      researcher:
        description: Read-only code researcher
        prompt: You only read code. Never edit.
        tools: [Read, Grep, Glob]
        model: sonnet
        maxTurns: 10
```

When to use: split work into a controller + specialist agents; isolate a sub-task with its own tool restrictions or a cheaper model.

Gotchas:
- Agent ids are kebab-case: `[a-z0-9]+(-[a-z0-9]+)*`. `my_agent` and `MyAgent` both reject.
- The `dag-node-skills` id is reserved by the `skills:` translation. Defining it yourself works (you win) but you lose the auto-generated skills wrapper — set `skills` directly on your agent definition.
- `options.agent` is intentionally not set when you use `agents:` — the main agent stays the primary, sub-agents are reachable only via the Task tool.
- Sub-agents inherit nothing from the parent's tool list. Whitelist tools on each one explicitly.

## Choosing between them

| Want to | Use |
|---------|-----|
| Bias the model toward a known skill | `skills:` |
| Let the model call an external API as a tool | `mcp:` |
| Auto-approve / deny tool calls deterministically | `hooks:` |
| Split work into specialists with separate tool budgets | `agents:` |
