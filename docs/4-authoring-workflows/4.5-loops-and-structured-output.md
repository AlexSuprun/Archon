# 4.5 Loops and structured output

What this answers: how to write iterative AI nodes correctly, and how to make node outputs machine-readable so downstream `when:` and prompts can rely on them.

## Loop node anatomy

Source: `packages/workflows/src/schemas/loop.ts`.

| Field | Required | Purpose |
|---|---|---|
| `loop.prompt` | yes | prompt re-evaluated each iteration |
| `loop.until` | yes | string the AI must emit to mark completion (e.g. `COMPLETE`) |
| `loop.max_iterations` | yes | hard cap; exceeding fails the node |
| `loop.fresh_context` | no (default `false`) | start a new session each iteration |
| `loop.until_bash` | no | shell command run after each iteration; exit `0` = complete |
| `loop.interactive` | no | pause between iterations for user feedback |
| `loop.gate_message` | required when `interactive: true` | prompt shown to user at the gate |

`retry:` is rejected on loop nodes — the loop is its own retry mechanism.

## Completion-signal pattern

The simplest loop. The AI prints `COMPLETE` when satisfied; otherwise it iterates.

```yaml
- id: refine
  loop:
    prompt: |
      Improve $DOCS_DIR/draft.md.
      When you think it's good enough, print exactly: COMPLETE
    until: COMPLETE
    max_iterations: 5
```

Detection is substring match on the assistant's final response. Pick a token unlikely to appear in normal prose.

## Bash gate (`until_bash`)

Use this when "done" is verifiable by a script (tests pass, lint clean, file exists). The bash gate runs after each iteration; exit 0 stops the loop.

```yaml
- id: fix-tests
  loop:
    prompt: "Read failing tests, fix the code. Re-run with: bun test"
    until: NEVER
    until_bash: bun test
    max_iterations: 8
```

`until` is still required by the schema; pick a string the AI will not emit.

## fresh_context + $LOOP_PREV_OUTPUT

Long sessions accumulate token cost and context drift. `fresh_context: true` starts each iteration as a new SDK session. The only carry-over is `$LOOP_PREV_OUTPUT` — the previous iteration's cleaned output.

Use it when:
- the task is stateless per iteration (lint, format, single-file refactor)
- you want to bound token usage per iteration
- the previous attempt's full transcript would distract more than help

```yaml
- id: rewrite
  loop:
    prompt: |
      Rewrite $1 for clarity. Previous attempt:
      ---
      $LOOP_PREV_OUTPUT
      ---
      Print COMPLETE when satisfied.
    until: COMPLETE
    max_iterations: 4
    fresh_context: true
```

On iteration 1, `$LOOP_PREV_OUTPUT` is `''`.

## Interactive loops

Pause between iterations for human feedback. Resume with `archon workflow approve <run-id> <feedback>`. The feedback lands in `$LOOP_USER_INPUT` **only on the first iteration after resume**.

```yaml
- id: edit
  loop:
    prompt: |
      Latest draft below. Apply the user's note: $LOOP_USER_INPUT
      Previous: $LOOP_PREV_OUTPUT
      Print COMPLETE when finished.
    until: COMPLETE
    max_iterations: 10
    interactive: true
    gate_message: "Review the draft. Approve to continue, or send a note."
```

Workflow-level `interactive: true` is required for approval-based runs on the web UI.

## Structured output (`output_format`)

`output_format` is a JSON Schema attached to an AI node. The provider returns JSON instead of free-form text. Source: `packages/workflows/src/schemas/dag-node.ts`, `packages/workflows/src/dag-executor.ts:445`.

| Provider | Behavior |
|---|---|
| `claude` | SDK-enforced via `outputFormat: { type: 'json_schema', schema }`. The assistant must emit JSON matching the schema. |
| `codex` | SDK-enforced via the same option. |
| `pi` | Best-effort. The schema is appended to the prompt and Pi's transcript is parsed as JSON post-hoc. May fail; downstream code must handle empty/string output. |

If `output_format` is set but the provider does not return structured output, the run logs a warning and downstream `when:` may not match.

### Example: classify and branch

```yaml
- id: classify
  prompt: |
    Classify "$ARGUMENTS".
  output_format:
    type: object
    properties:
      type: { type: string, enum: [BUG, FEATURE, QUESTION] }
      severity: { type: integer, minimum: 1, maximum: 5 }
    required: [type, severity]

- id: bug-flow
  depends_on: [classify]
  when: "$classify.output.type == 'BUG' && $classify.output.severity >= '3'"
  command: archon-triage
```

`when:` expressions support dot-notation field access: `$classify.output.type` parses the JSON output and reads the `type` key.

## When to reach for structured output

- The next node decides which branch to run (use `when: $node.output.field == '...'`).
- A bash/script node needs to consume the value (parse JSON in the script).
- Multiple downstream nodes need different fields from the same upstream answer.

For free-form prose hand-offs (drafts, summaries), keep the default plain text — JSON adds friction without payoff.
