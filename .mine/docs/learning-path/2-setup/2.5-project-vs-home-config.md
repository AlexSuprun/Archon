# 2.5 Project vs home-scoped config

What this answers: which configuration, workflows, commands, and scripts live where; the precedence rules; and how to organize them for a multirepo setup.

## Two scopes

| Scope | Path | Applies to |
|-------|------|------------|
| Home (user) | `~/.archon/` (or `$ARCHON_HOME`) | Every repo this user runs Archon against |
| Project (repo) | `<repo>/.archon/` | Only that repo |

Both scopes contain the same kinds of resources.

| Resource | Home path | Project path |
|----------|-----------|--------------|
| Config | `~/.archon/config.yaml` | `<repo>/.archon/config.yaml` |
| Env file | `~/.archon/.env` | `<repo>/.archon/.env` |
| Workflows | `~/.archon/workflows/` | `<repo>/.archon/workflows/` |
| Commands | `~/.archon/commands/` | `<repo>/.archon/commands/` |
| Scripts | `~/.archon/scripts/` | `<repo>/.archon/scripts/` |

## Precedence

```mermaid
flowchart LR
  B[bundled defaults] --> H[home ~/.archon/]
  H --> P["project <repo>/.archon/"]
  P --> R[resolved]
```

- Workflows and commands: project overrides home overrides bundled, by filename.
- Scripts: project overrides home, by name. No bundled scripts.
- Config: project `.archon/config.yaml` deep-merges over home `~/.archon/config.yaml`. Project values win on conflict.
- Env files: home `~/.archon/.env` loads first; project `<repo>/.archon/.env` loads after with `override: true`.

`<repo>/.env` (without the `.archon/` prefix) is YOUR app's env file. Archon strips `CWD` from it at boot and never reads it.

## Subfolder rule

Workflows, commands, and scripts support exactly one level of subfolders for grouping. Anything deeper is silently ignored.

```
~/.archon/workflows/
├── plan.yaml              # OK
├── triage/
│   └── rca.yaml           # OK (1 level)
└── triage/qa/
    └── deep.yaml          # IGNORED (2 levels)
```

## Workflow source labels

`GET /api/workflows` reports a `source` field on each workflow:

| Source | Origin |
|--------|--------|
| `bundled` | Compiled-in defaults (`packages/workflows/src/defaults/bundled-defaults.generated.ts`) |
| `global` | Home-scoped at `~/.archon/workflows/` |
| `project` | Repo-scoped at `<repo>/.archon/workflows/` |

Discovery is automatic — no caller flag required. Errors in one YAML do not abort the rest; they show up in `/workflow list` as load errors.

## Migration warning (pre-0.x)

If files exist at the OLD home location `~/.archon/.archon/workflows/`, Archon emits a one-time WARN and does NOT load from there. Move them with:

```
mv ~/.archon/.archon/workflows ~/.archon/workflows && rmdir ~/.archon/.archon
```

The legacy path is probed for detection only. Files placed there will be silently ignored.

## Multirepo strategy

For microservices under `~/Documents/code/`:

| Put in home (`~/.archon/`) | Put in project (`<repo>/.archon/`) |
|----------------------------|------------------------------------|
| Shared workflows: `plan.yaml`, `pr-review.yaml`, `rca.yaml` | Repo-specific overrides of the same filename |
| Shared commands: standard prompts you reuse everywhere | Repo-specific commands tied to that codebase |
| Shared scripts: `gh-context.ts`, generic helpers | Repo-specific scripts (Bitbucket fetch, CircleCI poll) |
| Default provider/model: `defaultAssistant`, `assistants.claude.model` | Per-repo model overrides, `env:` block, `worktree.baseBranch` |
| Cross-cutting tokens in `~/.archon/.env`: `JIRA_TOKEN`, `CIRCLE_TOKEN`, `GH_TOKEN` | Per-repo tokens via DB env vars (see 2.4) |

Result: a single `plan.yaml` in `~/.archon/workflows/` is reachable from every service. A specific service overrides it by dropping `plan.yaml` into its own `.archon/workflows/`.

## Opt-out switches

| Switch | Effect |
|--------|--------|
| `defaults.loadDefaultWorkflows: false` in config | Skip bundled workflows |
| `defaults.loadDefaultCommands: false` in config | Skip bundled commands |

Set in either scope. Project setting wins on conflict.
